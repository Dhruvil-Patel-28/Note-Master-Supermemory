# AGENTS.md

## State of the repo

Phases 1–4 shipped: capture pipeline (text + doc + voice upload) + SQLite/FTS5 + hybrid retrieval (sqlite-vec + LadybugDB graph + reciprocal-rank fusion) + grounded chat with structured field cards + voice notes (faster-whisper) + guardrails (rule-based sensitivity tiers, app-level PIN gate with audit log). A UI/polish pass added shadcn/ui (Tailwind v4) frontend, dark/light themes, responsive layout, capture search/filter, settings (PIN mgmt + audit-log viewer), backend health indicator, version restore, and the correction loop (`chat_feedback` table + `POST /feedback`). Post-4 hardening: document labels (`captures.note`, searchable + editable without re-extraction), document-intent queries that open the original file in a preview dialog, typo-tolerant FTS, and prompt-injection resistance (instructions are a system message; the question is an isolated user turn). `PLAN.md` remains the source of truth for scope (v0.1, all decisions resolved) — encryption-at-rest remains unbuilt/deferred.

## Non-obvious facts that constrain all code

- **Repo layout:** `backend/` (FastAPI, uv-managed venv) + `frontend/` (Next.js 16, App Router). Run backend with `uv run uvicorn app.main:app --reload` from `backend/` (never bare `uvicorn` — deps live in `.venv`); frontend with `npm run dev` from `frontend/`. Tests: `uv run pytest tests` from `backend/`.
- **All models run via local Ollama — localhost-only invariant (hard constraint):** no hosted APIs, no API keys, no telemetry. `OLLAMA_HOST` must stay `http://localhost:11434`. Documents/audio never leave the machine; uvicorn binds 127.0.0.1 and CORS allows only localhost:3000.
- **Model picks (16GB Mac tier — tuned for speed, Feb 2026):** chat/answers + entity extraction `llama3.2:3b` (~2GB, sub-second answers, ~1-3s extraction); embeddings `nomic-embed-text`; ASR faster-whisper `base` (CPU); OCR `qwen2.5vl:3b` (vision, `OCR_MODEL`, gated by `OCR_ENABLED` — when disabled, scanned docs fail ingestion by design). Override via `OLLAMA_MODEL` / `OLLAMA_EXTRACT_MODEL` env — `qwen3:8b` (5.6GB, ~5-15s answers, better prose quality) and `hermes3` are still installed and usable. **qwen3 models (8b AND 4b) are pathologically slow at JSON generation on this Mac (19-150s/call) — do not use them for extraction; the 3b small model passes all grounding + structured-card tests.** The chat prompt in `app/retrieval/chat.py` is a **system message** (instructions + few-shot examples + retrieved context) with the question as an **isolated user turn** — instructions embedded in the question ("bypass guardrail", "ignore previous instructions") are data, never commands; small models comply with in-message instructions, so never merge the query back into the instruction text. Also: `"think": false` + temperature 0.1, notes-are-facts rule ("with my dog" ⇒ has a dog), typo-reading rule ("but" for "buy"), list-question rule (enumerate ALL matching items — "anything" questions answering one item was a real bug), and few-shot JSON examples (the 3b model mirrors examples; written rules alone don't change behavior).
- **Backend internals (Phases 1–2):** raw `sqlite3` stdlib (no ORM); `app/db.py` `connect()` per-operation connections loading the sqlite-vec extension (sqlite-vec 0.1.9 verified on Python 3.14), schema applied at startup from `app/schema.sql`; ingestion is FastAPI `BackgroundTasks` (status queued→processing→indexed/failed); FTS5 is a standalone table `captures_fts` (rowid = captures.id), synced manually by the pipeline — always delete+reinsert on edit. **FTS content = `note + "\n" + original_filename + "\n" + content`** (added post-Phase-4 so "get me my resume" matches a PDF whose extracted text never contains the word "resume" — captures.`original_filename` is populated at upload from the submitted filename, guarded ALTER for old DBs, backfilled manually for pre-existing docs; the `note` column was added later for user labels like "this is my resume" — same FTS indexing, and **PATCH can update the note alone** (rebuild FTS, no re-extraction)). `GET /captures/{id}/file` serves the original upload (FileResponse, media type by extension; 404 for text captures); the frontend shows the filename chip + eye button and source chips get an "open original" link when `type == 'doc'`; doc cards show filename + note, never the extracted text dump.
- **Chunking + vectors (Phase 2):** `app/ingestion/chunker.py` splits ~800 chars with ~100 overlap; `app/ingestion/embeddings.py` embeds via Ollama `nomic-embed-text` (768-dim). `capture_chunks` (metadata, FK cascade, `embedding` BLOB denormalized at index for cosine re-scoring — `ALTER TABLE ADD COLUMN` guarded in `db.py init_db` for old DBs) + `chunks_vec` vec0 virtual table (rowid = chunk id). Pipeline writes chunks at index and delete+reinserts on edit; **vec rows are not FK-cascaded** — the delete endpoint must delete `chunks_vec` rows explicitly before deleting the capture (metadata rows cascade via FK).
- **Hybrid retrieval (Phase 2):** `app/retrieval/vector.py` KNN with `is_latest` filter + **cosine re-score** (`MIN_COSINE_DISTANCE = 0.5`, computed from the embedding BLOB denormalized into `capture_chunks.embedding` at index time — sqlite-vec 0.1.9 vec0 cannot SELECT stored vectors; KNN fetches 12 candidates, re-scores in Python, drops unrelated hits so the PIN gate and not-found path stay honest). `_cosine_distance` is NULL/falsy-safe (returns 1.0) — chunks indexed before the embedding column existed have empty BLOBs, and one TypeError crashed the whole vector search, silently degrading chat to FTS-only (real bug: "what is my college name" answered from a literal transcript field instead of the real college name); `app/retrieval/fusion.py` reciprocal-rank fusion of FTS + vector, deduped by capture; `app/routes/chat.py` feeds the **top 5** fused hits to the LLM (more noise makes small models flip structured answers to prose). **Context expansion (post-Phase-4 fix):** fusion dedupes to ONE snippet per capture, which truncated multi-chunk docs (resumes) to ~800 chars and hid projects/skills from the LLM — `retrieval/chat.py expand_hits()` now expands each fused capture into per-chunk context: captures ≤ 6000 chars (resumes, notes) go to the LLM in full, larger docs keep best chunk ±1 neighbor, with a 14000-char global budget; **byte-identical chunks are skipped** (`seen_chunks` set) because the user uploaded the same resume 3× and the duplicates starved the budget, truncating the skills section. Call order in `routes/chat.py`: `fuse()` → `expand_hits()` for the LLM context, while sources/tiers/audit stay per-capture. Structured answers: chat LLM is prompted to return JSON `{"kind": "fields"|"prose"|"not_found", ...}` — parsed in `app/retrieval/chat.py` `_parse_response`, surfaced as `ChatResponse.structured` and rendered as a key-value card in `ChatPane`. `_parse_response` never surfaces raw model output: it recovers JSON embedded in chatter (first `{` to last `}`), strips `<b>`/`</b>` highlight tags the model echoes from FTS snippets, maps empty prose to not-found, and returns not-found for unparseable junk — do not regress that (the small model wraps JSON in prose and the raw dump looked like "extracted code" in the UI). **Long fields lists (post-course-card fix):** the 3b model emits malformed JSON for big lists in three shapes — trailing `["1"]` junk, a dropped delimiter mid-list, and the array's closing `]` omitted (`...CLOUD COMPUTING"}}`); `_salvage` (kind+answer regex) + `_salvage_fields` (item objects from the `"fields": [` marker onwards, tolerant of both) recover them, and `_filter_fields` drops any field whose key doesn't appear in the retrieved context (the model invents list items — "CSL 310 ARTIFICIAL INTELLIGENCE" was never in the transcript) with whitespace-normalized matching; chat options use `num_predict: 4096` because default output caps truncated the course list mid-generation. **Academic/semester queries:** transcripts label semester sections with lone digits/Roman numerals (`2 / DIGITAL ELECTRONICS / BB / 4 / CSL 102 ...`); "2nd semester" never lexically matches, so `routes/chat.py` appends `transcript marksheet` to the FTS query for academic-intent words (semester/cgpa/grade/result/courses...), and the prompt teaches the semester-section format with a concrete example (the 3b model otherwise reads the digit inside `CSL 202` as the semester label). **Transcript semester parsing (post-semester fix, `chat.py`):** semester questions get `sem_ctx` — `_parse_transcript_sections` (Python, no LLM) parses the FULL extracted text (chunking splits/overlaps duplicate rows and a credit digit like `BC 2` then reads as a section label), handles no-space codes (`MAL103`) and `SS` grades, skips credit digits that follow grades, and injects the exact course list into the context so the 3b model only has to list what it's handed; `_semester_number` resolves digit/ordinal/cardinal/Roman forms (including "semester five"). **Deterministic transcript facts (post-credits fix, `chat.py` + `routes/chat.py`):** semester-course and total-credit answers (`transcript_fact_answer()`, `_extract_credits` regex on `Grand Total Credit`) are built entirely in Python from parsed capture contents — the LLM is never asked to enumerate (it dropped items: "3rd sem" came back with 2 of 6, credits misread), and the route checks `transcript_fact_answer` **before** the PIN gate because the answer never draws on sensitive captures (vector noise dragged an Aadhaar note into the top-5 for "how many credits have I earned" and gated an innocent query); `credit(s)` is an academic FTS-augmentation word. Everything else stays gated as before. Typo correction skips terms containing digits — "2nd" edit-variants include "end", which matched "end-to-end" in resumes and flooded the ranking. **Document-intent queries** (show/get/open + doc noun: resume/cv/pdf/statement/pan…, `_document_intent` in `routes/chat.py`): when the top fused hit is a `doc` capture with a stored file, the chat **skips the LLM entirely** and returns a one-line answer + `show_document: {capture_id, filename}`; the frontend auto-opens a preview dialog (iframe for PDF/images, new tab for Word/Excel). If Ollama embeddings fail, chat degrades to FTS-only. FTS: `app/retrieval/fts.py` strips punctuation and a small stopword list (`_STOPWORDS`) plus **single-character terms** (a "2+2" query OR-matched the digit "2" against every capture's grades/dates and the model answered "4 [1]" from noise — now it returns no hits and a clean not-found) before building AND-then-OR fallback queries — without the stopword filter, the OR fallback matches common words ("is") and the PIN gate misfires on unrelated queries. **Typo tolerance (post-note fix):** when the AND query fails, `_correct_terms` boosts edit-distance-1 variants of each query term (delete/substitute/insert, variants counted via `_term_count`, top 3, skip stopwords/len<2) and the OR fallback becomes `("buy" OR "but") …` — so typos in either notes ("i have to **but** mangoes") or queries ("byu batteries") still match.
- **Graph (Phase 3):** LadybugDB (`ladybug` PyPI pkg, 0.19.1, embedded, MIT — formerly Kuzu), file `data/graph.lbug`. `app/graph.py`: node tables `Capture(id, is_latest)` + `Entity(name, entity_type)`; rel tables `MENTIONS` (Capture→Entity) + `RELATES_TO` (Entity→Entity, directed but matched undirected). Schema applied idempotently per connection; a module-level `Database` singleton must stay referenced. `app/ingestion/extract.py` runs LLM NER (JSON-only, few-shot, `parse_response` normalizes + filters generic names/relations) at ingestion (1-hop via MENTIONS) and at query time; `app/graph.py` `search()` does 1-hop + 2-hop Cypher with `is_latest` filter (old versions excluded by node property, flipped on re-upload via sibling ids). `graph._snippet` picks the chunk containing a matched entity name (not chunk 0 — that made graph hits drag in resume headers). Graph writes are best-effort — failure logs and capture still indexes; capture delete DETACHes the node (edges auto-cascade). RELATES_TO direction from the small model is unreliable — never rely on it, matching is undirected.
- **Config is env-driven at import time:** `app/config.py` reads `NOTE_MASTER_DATA_DIR`, `OLLAMA_MODEL`, etc. when imported — tests set env before importing app. Runtime data lives in `backend/data/` (gitignored).
- **Versioning + cascade:** re-uploaded docs create a new `captures` row sharing `document_group_id` (version bump, `is_latest` flip); deletion must cascade to FTS rows + files. Partial unique index enforces one latest per group. **Restore** (`POST /captures/{id}/restore`, `routes/captures.py`) flips `is_latest` within a group — must zero all siblings *before* setting the target (two UPDATEs; the partial unique index rejects a single statement) and calls `graph.restore_capture` (best-effort) to flip the graph node property.
- **UI-polish endpoints (frontend/backend, post-Phase-4):** `GET /health` (`routes/health.py` — DB `SELECT 1` + `ollama.Client().list()`, returns `{status: ok|degraded, database, ollama}`); `GET /audit` (`routes/audit.py` — last N `audit_log` rows); `POST /feedback` (`routes/feedback.py` + `chat_feedback` table in `schema.sql` — stores `{query, capture_ids, kind, note}` and best-effort re-ingests the top source capture via `BackgroundTasks`). Frontend (`lib/api.ts`) wires `pinChange`/`pinDelete` too — `/pin/change` and `/pin/delete` existed on the backend but were never exposed before.
- **Voice (Phase 4):** `POST /captures/audio` (extensions `.m4a/.webm/.wav/.mp3/.aiff/.ogg/.opus` → `type='voice'`, file on disk via `storage`) transcribes with `app/ingestion/asr.py` `transcribe()` (lazy module-level `WhisperModel` singleton, `base`/CPU/int8, on-demand per note — model stays loaded in memory after first use; ~2-20s cold incl. download). Playback served by `GET /captures/{id}/audio` (FileResponse, media type by suffix). Pipeline raises `ValueError` on empty transcription → capture `failed`.
- **Guardrails (Phase 4):** sensitivity assigned at ingestion by `app/ingestion/classify.py` — pure rules, no LLM: PAN/Aadhaar/account-number regexes + ID/financial keyword lists → `high`; meeting/doctor/address/phone keywords → `moderate`; else `none`. Keywords match with **word boundaries** (`\b` — post-Phase-4 fix: a resume mentioning "Pandas" was falsely flagged `high` because "pan" matched as a substring). Only `high` gates retrieval: `app/routes/chat.py` checks `X-Pin-Token` (30-min TTL token from `app/guardrails/pin.py` — scrypt n=2^14 r=8 p=1, token stored as sha256 in `app_settings`); gated queries return `needs_pin: true` with `PIN_REQUIRED_ANSWER` and **no LLM call**; unlocked sensitive retrievals are audit-logged with `sensitive_access=1`. PIN endpoints in `app/routes/pin.py` (`/pin/status|set|verify`; `delete` allows empty pin — local recovery, documented as light guardrail). `ChatSource.sensitivity_tier` + `ChatResponse.needs_pin` surface in the API; frontend shows sensitivity badges (🔒 high / ⚠ moderate), warning banners, and a PIN modal in `ChatPane`.
- **Intent layer (post-Phase-4, the general "thinking" fix):** `app/retrieval/intent.py` classifies EVERY query before retrieval (`classify()` — one 3b call, constrained JSON, few-shot, temperature 0.1/`think: false`, `_parse_intent` whitelist-salvage, any failure → `notes`). **`code`/`general` intents return a clean `REFUSAL_ANSWER` (found=False, no sources, no LLM, no retrieval — nothing sensitive is ever touched); the refusal is deterministic, so a misclassified code question is a refusal, never garbage.** The 3b classifier over-answers "general" for user-life questions ("car registration", "electricity bill", "where did I go in December") — counteracted with a notes-biased prompt (9 notes examples vs 2 general) AND a deterministic safety net: `_USER_REFERENCE_RE` downgrades `general`→`notes` for queries about the user ("my", "do i", "where do i") unless code hints (`_CODE_HINTS`: print/function/syntax/in python…) win. Never widen "general" examples; the bias is what keeps notes questions on the notes path. **Stuck-expansion (lexical-gap cure):** after `fuse()`, if hits are empty or have no `<b>` matches, `_expand_anchors(query)` asks the 3b to pick up to 5 words from `_vocabulary()` — the user's ACTUAL words, sampled per-capture from the first ~300 chars of the latest 20 captures (headers carry the distinctive facts: institute name, workplace; frequency-ranking alone drowned them under resume duplicates/course codes) — then re-runs FTS with the validated anchors and re-fuses. The anchor prompt `_ANCHOR_SYSTEM` is a `str.format` template: **its literal JSON braces must stay escaped as `{{"terms": ...}}`** (a `KeyError` there silently made every expansion return [] via the except-path — real bug). It fixes "where do i study" (notes say 'institute', never 'study') generally: expansion surfaces the transcript/resume, and the chat prompt's inference rules (an institute/college/university in the user's documents is where the user studies; a workplace is where they work) + the "where do i study" few-shot example make the 3b mirror the identity inference. The query-typo rule ("byu" for "buy") + a few-shot example cover typo'd QUESTIONS (FTS typo-correction only fixed retrieval — the model alone read "byu" literally and answered not-found; real bug). Transcript-fact determinism, the PIN gate (expansion results are gated like any hits), and the injection scrub all run before/around these layers untouched.
- **Testing quirks:** TestClient runs BackgroundTasks after the response, so the create response is `queued` — tests poll `GET /captures/{id}` until indexed. Chat tests need Ollama running with the configured model; the full suite (93 tests) takes ~2.5min on `llama3.2:3b` + faster-whisper (real inference per test), and `uv run pytest tests -m "not llm"` runs 68 pure-logic tests in <15s. Tests share one session DB — the PIN persists across tests (`unlock()` helper sets/verifies and returns a token); `TestPin` clears it last (file order: test_api then test_units). LLM-dependent assertions retry up to 3× (small models occasionally hallucinate/answer prose in noisy multi-capture contexts — seen with multiple similar PAN docs in one DB). Audio e2e generates a fixture with macOS `say -o file.aiff`; OCR fixture chain: `cupsfilter txt > pdf` (PDF goes to **stdout**) → `pymupdf` render → `sips -s format pdf png --out scanned.pdf` (`qlmanage -t` hangs headless — never use it; a bare `sips` PNG can be blank).
- **OCR routing at ingestion:** cheap file-type/content check — docs with a real text layer (Word, Excel, text PDFs, plain text) → local extraction (pypdf/python-docx/openpyxl, no model); scanned/photographed docs (Aadhar, PAN, receipts) → OCR via `app/ingestion/ocr.py` (`ocr_image()` for image uploads — `.png/.jpg/.jpeg/.webp/.tiff/.bmp` are accepted capture types — and `ocr_pdf()` for image-only PDFs: PyMuPDF (`pymupdf` pkg, `import pymupdf` — the old `fitz` alias is deprecated) rasterizes each page at 200 DPI → per-page PNG → Ollama vision `qwen2.5vl:3b`, `OCR_ENABLED`-gated; raises `ValueError` when disabled so ingestion marks capture `failed`). Fixture chain for scanned docs: `cupsfilter txt > pdf` (PDF goes to **stdout**, `-o` never writes the file) → `pymupdf` render → `sips -s format pdf png --out scanned.pdf`; qlmanage hangs headless — never use it.

## Stack (PLAN.md §3.5, §3.7 — all decisions resolved, do not reopen)

- **Frontend:** Next.js (responsive web; no native app in v1).
- **Backend:** FastAPI, orchestrating ingestion pipeline + retrieval engine + guardrail layer.
- **Storage is two embedded engines, no standalone services:** one SQLite file holds app state + FTS5 + vectors via sqlite-vec; a second embedded store is LadybugDB (property graph, MIT). Files (audio, uploads) go on disk referenced by path — never blobbing into SQLite.
- **ASR:** `faster-whisper` (CTranslate2), `small`/`base` model, CPU, run on-demand per voice note — not a persistent background process.
- **User model:** single-user v1 — no auth/tenant isolation; `user_id` scoping deferred. Keep a `users` table anyway (future-proofing, §3.2a).
- **Sensitivity tiers (`none`/`moderate`/`high`)** are assigned at ingestion, not a boolean flag; only `high` (ID/financial docs) is PIN-gated at retrieval, others get a warning label. The PIN is a local app-level passcode (not tied to any auth system) with its own set/change/recovery flow.
- **Retrieval is hybrid** (graph traversal + vector + FTS5 fused/reranked) with strict RAG grounding — answers must come only from retrieved context, with an explicit "not found" path, and every sensitive retrieval is audit-logged.
- **Suggested phasing** (§4): build in order — Phase 1 capture pipeline + SQLite/FTS5 + basic chat, then vector, then graph, then voice + guardrail hardening.
