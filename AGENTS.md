# AGENTS.md

## State of the repo

Phases 1–4 shipped: capture pipeline (text + doc + voice upload) + SQLite/FTS5 + hybrid retrieval (sqlite-vec + LadybugDB graph + reciprocal-rank fusion) + grounded chat with structured field cards + voice notes (faster-whisper) + guardrails (rule-based sensitivity tiers, app-level PIN gate with audit log). `PLAN.md` remains the source of truth for scope (v0.1, all decisions resolved) — Phase 5+ (correction loop, encryption-at-rest) is unbuilt/deferred.

## Non-obvious facts that constrain all code

- **Repo layout:** `backend/` (FastAPI, uv-managed venv) + `frontend/` (Next.js 16, App Router). Run backend with `uv run uvicorn app.main:app --reload` from `backend/` (never bare `uvicorn` — deps live in `.venv`); frontend with `npm run dev` from `frontend/`. Tests: `uv run pytest tests` from `backend/`.
- **All models run via local Ollama — localhost-only invariant (hard constraint):** no hosted APIs, no API keys, no telemetry. `OLLAMA_HOST` must stay `http://localhost:11434`. Documents/audio never leave the machine; uvicorn binds 127.0.0.1 and CORS allows only localhost:3000.
- **Model picks (16GB Mac tier — tuned for speed, Feb 2026):** chat/answers + entity extraction `llama3.2:3b` (~2GB, sub-second answers, ~1-3s extraction); embeddings `nomic-embed-text`; ASR faster-whisper `base` (CPU); OCR `qwen2.5vl:3b` (vision, `OCR_MODEL`, gated by `OCR_ENABLED` — when disabled, scanned docs fail ingestion by design). Override via `OLLAMA_MODEL` / `OLLAMA_EXTRACT_MODEL` env — `qwen3:8b` (5.6GB, ~5-15s answers, better prose quality) and `hermes3` are still installed and usable. **qwen3 models (8b AND 4b) are pathologically slow at JSON generation on this Mac (19-150s/call) — do not use them for extraction; the 3b small model passes all grounding + structured-card tests.** The chat prompt in `app/retrieval/chat.py` uses a hardened grounding instruction ("never use your own knowledge") + `"think": false` + temperature 0.1 — small models ignore weaker wording.
- **Backend internals (Phases 1–2):** raw `sqlite3` stdlib (no ORM); `app/db.py` `connect()` per-operation connections loading the sqlite-vec extension (sqlite-vec 0.1.9 verified on Python 3.14), schema applied at startup from `app/schema.sql`; ingestion is FastAPI `BackgroundTasks` (status queued→processing→indexed/failed); FTS5 is a standalone table `captures_fts` (rowid = captures.id), synced manually by the pipeline — always delete+reinsert on edit.
- **Chunking + vectors (Phase 2):** `app/ingestion/chunker.py` splits ~800 chars with ~100 overlap; `app/ingestion/embeddings.py` embeds via Ollama `nomic-embed-text` (768-dim). `capture_chunks` (metadata, FK cascade, `embedding` BLOB denormalized at index for cosine re-scoring — `ALTER TABLE ADD COLUMN` guarded in `db.py init_db` for old DBs) + `chunks_vec` vec0 virtual table (rowid = chunk id). Pipeline writes chunks at index and delete+reinserts on edit; **vec rows are not FK-cascaded** — the delete endpoint must delete `chunks_vec` rows explicitly before deleting the capture (metadata rows cascade via FK).
- **Hybrid retrieval (Phase 2):** `app/retrieval/vector.py` KNN with `is_latest` filter + **cosine re-score** (`MIN_COSINE_DISTANCE = 0.5`, computed from the embedding BLOB denormalized into `capture_chunks.embedding` at index time — sqlite-vec 0.1.9 vec0 cannot SELECT stored vectors; KNN fetches 12 candidates, re-scores in Python, drops unrelated hits so the PIN gate and not-found path stay honest); `app/retrieval/fusion.py` reciprocal-rank fusion of FTS + vector, deduped by capture; `app/routes/chat.py` feeds the **top 5** fused hits to the LLM (more noise makes small models flip structured answers to prose). Structured answers: chat LLM is prompted to return JSON `{"kind": "fields"|"prose"|"not_found", ...}` — parsed in `app/retrieval/chat.py` `_parse_response`, surfaced as `ChatResponse.structured` and rendered as a key-value card in `ChatPane`. If Ollama embeddings fail, chat degrades to FTS-only. FTS: `app/retrieval/fts.py` strips punctuation and a small stopword list (`_STOPWORDS`) before building AND-then-OR fallback queries — without this, the OR fallback matches common words ("is") and the PIN gate misfires on unrelated queries.
- **Graph (Phase 3):** LadybugDB (`ladybug` PyPI pkg, 0.19.1, embedded, MIT — formerly Kuzu), file `data/graph.lbug`. `app/graph.py`: node tables `Capture(id, is_latest)` + `Entity(name, entity_type)`; rel tables `MENTIONS` (Capture→Entity) + `RELATES_TO` (Entity→Entity, directed but matched undirected). Schema applied idempotently per connection; a module-level `Database` singleton must stay referenced. `app/ingestion/extract.py` runs LLM NER (JSON-only, few-shot, `parse_response` normalizes + filters generic names/relations) at ingestion (1-hop via MENTIONS) and at query time; `app/graph.py` `search()` does 1-hop + 2-hop Cypher with `is_latest` filter (old versions excluded by node property, flipped on re-upload via sibling ids). Graph writes are best-effort — failure logs and capture still indexes; capture delete DETACHes the node (edges auto-cascade). RELATES_TO direction from the small model is unreliable — never rely on it, matching is undirected.
- **Config is env-driven at import time:** `app/config.py` reads `NOTE_MASTER_DATA_DIR`, `OLLAMA_MODEL`, etc. when imported — tests set env before importing app. Runtime data lives in `backend/data/` (gitignored).
- **Versioning + cascade:** re-uploaded docs create a new `captures` row sharing `document_group_id` (version bump, `is_latest` flip); deletion must cascade to FTS rows + files. Partial unique index enforces one latest per group.
- **Voice (Phase 4):** `POST /captures/audio` (extensions `.m4a/.webm/.wav/.mp3/.aiff/.ogg/.opus` → `type='voice'`, file on disk via `storage`) transcribes with `app/ingestion/asr.py` `transcribe()` (lazy module-level `WhisperModel` singleton, `base`/CPU/int8, on-demand per note — model stays loaded in memory after first use; ~2-20s cold incl. download). Playback served by `GET /captures/{id}/audio` (FileResponse, media type by suffix). Pipeline raises `ValueError` on empty transcription → capture `failed`.
- **Guardrails (Phase 4):** sensitivity assigned at ingestion by `app/ingestion/classify.py` — pure rules, no LLM: PAN/Aadhaar/account-number regexes + ID/financial keyword lists → `high`; meeting/doctor/address/phone keywords → `moderate`; else `none`. Only `high` gates retrieval: `app/routes/chat.py` checks `X-Pin-Token` (30-min TTL token from `app/guardrails/pin.py` — scrypt n=2^14 r=8 p=1, token stored as sha256 in `app_settings`); gated queries return `needs_pin: true` with `PIN_REQUIRED_ANSWER` and **no LLM call**; unlocked sensitive retrievals are audit-logged with `sensitive_access=1`. PIN endpoints in `app/routes/pin.py` (`/pin/status|set|verify`; `delete` allows empty pin — local recovery, documented as light guardrail). `ChatSource.sensitivity_tier` + `ChatResponse.needs_pin` surface in the API; frontend shows sensitivity badges (🔒 high / ⚠ moderate), warning banners, and a PIN modal in `ChatPane`.
- **Testing quirks:** TestClient runs BackgroundTasks after the response, so the create response is `queued` — tests poll `GET /captures/{id}` until indexed. Chat tests need Ollama running with the configured model; the full suite (43 tests) takes ~70-85s on `llama3.2:3b` + faster-whisper (real inference per test), and `uv run pytest tests -m "not llm"` runs pure logic in <1s. Tests share one session DB — the PIN persists across tests (`unlock()` helper sets/verifies and returns a token); `TestPin` clears it last (file order: test_api then test_units). LLM-dependent assertions retry up to 3× (small models occasionally hallucinate/answer prose in noisy multi-capture contexts — seen with multiple similar PAN docs in one DB). Audio e2e generates a fixture with macOS `say -o file.aiff`; OCR fixture via `cupsfilter`→`qlmanage -t` (a bare `sips` PNG can be blank).
- **OCR routing at ingestion:** cheap file-type/content check — docs with a real text layer (Word, Excel, text PDFs) → local extraction (pypdf/python-docx/openpyxl, no model); scanned/photographed docs (Aadhar, PAN, receipts) → OCR via `app/ingestion/ocr.py` `ocr_image()` (Ollama vision `qwen2.5vl:3b`, base64 image, `OCR_ENABLED`-gated; raises `ValueError` when disabled so ingestion marks capture `failed`).

## Stack (PLAN.md §3.5, §3.7 — all decisions resolved, do not reopen)

- **Frontend:** Next.js (responsive web; no native app in v1).
- **Backend:** FastAPI, orchestrating ingestion pipeline + retrieval engine + guardrail layer.
- **Storage is two embedded engines, no standalone services:** one SQLite file holds app state + FTS5 + vectors via sqlite-vec; a second embedded store is LadybugDB (property graph, MIT). Files (audio, uploads) go on disk referenced by path — never blobbing into SQLite.
- **ASR:** `faster-whisper` (CTranslate2), `small`/`base` model, CPU, run on-demand per voice note — not a persistent background process.
- **User model:** single-user v1 — no auth/tenant isolation; `user_id` scoping deferred. Keep a `users` table anyway (future-proofing, §3.2a).
- **Sensitivity tiers (`none`/`moderate`/`high`)** are assigned at ingestion, not a boolean flag; only `high` (ID/financial docs) is PIN-gated at retrieval, others get a warning label. The PIN is a local app-level passcode (not tied to any auth system) with its own set/change/recovery flow.
- **Retrieval is hybrid** (graph traversal + vector + FTS5 fused/reranked) with strict RAG grounding — answers must come only from retrieved context, with an explicit "not found" path, and every sensitive retrieval is audit-logged.
- **Suggested phasing** (§4): build in order — Phase 1 capture pipeline + SQLite/FTS5 + basic chat, then vector, then graph, then voice + guardrail hardening.
